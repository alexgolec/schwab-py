Announcing ``schwab-py`` v2.0
=============================

Reviving Regular Maintenance
----------------------------

After a prolonged hiatus `for good reasons, I promise <https://discord.com/
channels/720378361880248621/1062730209943629915/1570943743467462781>`__, I am
returning to actively maintaining ``schwab-py``! In the interim, we've seen good
developments, like the community developing some very interesting forks and
submitting some very important requests, as well as some bad developments, like
deprecation warnings and bugs creeping in. I am now actively working through the
outstanding issues with the library, as well as incorporating some of the
interesting ideas suggested and implemented by community members.

V2 Transition Timeline
----------------------

Some of the changes I am exploring are unfortunately breaking changes. For
instance, the migration from the deprecated ``httpx`` to the supported
``httpx2`` results in a different exposed exception hierarchy, which will cause
existing code to break. In order to preserve compatibility with existing code,
these new changes will be released as a ``2.x`` version series. 

In order to minimize the impact on users, we will implement a transition plan:

* All ``1.x`` releases will feature a deprecation warning admonishing users to
  either prepare to transition to 2.0 or pin their versions to ``<2.0`` in their
  package managers.
* ``2.0`` will be made available as an extended series of ``alpha`` and ``beta``
  releases prior to release, effectively turning it into an optional release for
  a time. During this prerelease period, the interface will be subject to
  change.
* Once the interface stabilizes, a series of one or more ``2.0`` release
  candidates will be released with the finalized interface.
* The final ``2.0rc(x)`` release candidate will be released as ``2.0`` no less
  than 90 days after the first ``1.x`` release featuring the deprecation
  warning, and no less than 14 days after the final ``2.0`` release candidate.
  This way, users who are still on ``1.x`` have an opportunity to learn about
  and prepare for the upcoming upgrade, and users following along with the
  development of ``2.0`` can adjust to the stable interface.
* All development will be accompanied by frequent updates in the `support
  channel on the project discord server
  <https://discord.com/invite/mm44rstRCg>`__.

Compatibility Changes
---------------------

This section lists the substantive differences between ``1.x`` and ``2.0``.

``httpx`` replaced with ``httpx2``
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

All HTTP is now performed by `httpx2 <https://www.python-httpx.org>`__, the
actively maintained successor to ``httpx``. Response objects, status codes,
timeouts, and client configuration are API-compatible, so most users will
notice no difference. However, ``httpx`` and ``httpx2`` define *separate* class
hierarchies, so code that references ``httpx`` types directly will need
updating:

* ``except httpx.HTTPError`` (and other ``httpx`` exception types) will **not**
  catch errors raised by this library. Update exception handling to use
  ``httpx2`` exceptions.
* ``isinstance(response, httpx.Response)`` checks and ``httpx.Response`` type
  annotations will fail against our return values. Use ``httpx2.Response``.
* The ``httpx`` logger is renamed ``httpx2``; update logging configuration
  accordingly.

Websocket implementation updated
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Streaming now uses ``websockets.asyncio`` (the maintained implementation)
instead of the deprecated ``websockets.legacy``. This is transparent for most
users, but arguments passed via ``websocket_connect_args`` to
:func:`schwab.auth.easy_client` are forwarded verbatim to
``websockets.asyncio.client.connect``, whose signature differs from the legacy
``connect``:

* ``extra_headers`` is renamed ``additional_headers``
* ``create_protocol`` is renamed ``create_connection`` with a different
  signature
* ``read_limit`` is removed

New options are also available, including ``proxy``, ``reconnect_delays``,
and ``process_exception``. See the `websockets asyncio client documentation
<https://websockets.readthedocs.io/en/stable/reference/asyncio/client.html#websockets.asyncio.client.connect>`__
for the full signature.

Prices must be strings
~~~~~~~~~~~~~~~~~~~~~~

``OrderBuilder.set_price``, ``OrderBuilder.set_stop_price``, and the order
templates that call them now require prices as strings. Passing ``float``
(or any other non-string value) raises ``ValueError``; the deprecated
``truncate_float`` conversion path is removed, along with the warning it
emitted. Callers previously relying on float conversion must format prices
themselves — e.g., ``f'{price:.2f}'``.

All price strings pass through verbatim for Schwab to validate, with one
exception: strings that parse to a negative number raise ``ValueError``,
because the Schwab API silently strips the sign from ``price`` and
``stopPrice`` fields — a negative input would otherwise be submitted as its
absolute value, inverting the order's intent. ``copy_price`` and
``copy_stop_price`` still bypass validation as before.

Contracts Around ``date`` and ``datetime`` Parameters
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

V1's use of ``date`` and ``datetime`` for specifying moments in time and days
was inconsistent and, in some cases, subtly but importantly incorrect. They were
also out of sync with the behavior of Schwab API itself. 

V2 reforms its use of dates and times to be more correct, and to accurately
reflect the actual values expected by the Schwab API itself. It makes the
following changes:

* Timezones are now required for methods which accept ``datetime`` objects to
  specify instants in time. Code which generates timezone-naive instances
  such as using ``datetime.now()`` will now see methods raise ``ValueError``
  instead of accepting these values. For example, the call to ``datetime.now()``
  must be replaced by one which passes a time zone explictly such as
  ``datetime.datetime.now(zoneinfo.ZoneInfo('America/New_York'))``.
  
  The methods with these new semantics are:

   * :meth:`get_orders_for_account <schwab.client.Client.get_orders_for_account>`
   * :meth:`get_orders_for_all_linked_accounts <schwab.client.Client.get_orders_for_all_linked_accounts>`
   * :meth:`get_transactions <schwab.client.Client.get_transactions>`
   * :meth:`get_price_history <schwab.client.Client.get_price_history>`
   * :meth:`get_price_history_every_minute <schwab.client.Client.get_price_history_every_minute>`
   * :meth:`get_price_history_every_five_minutes <schwab.client.Client.get_price_history_every_five_minutes>`
   * :meth:`get_price_history_every_ten_minutes <schwab.client.Client.get_price_history_every_ten_minutes>`
   * :meth:`get_price_history_every_fifteen_minutes <schwab.client.Client.get_price_history_every_fifteen_minutes>`
   * :meth:`get_price_history_every_thirty_minutes <schwab.client.Client.get_price_history_every_thirty_minutes>`

* Methods which accept calendar days as inputs now require ``datetime.date``
  objects. Note that even though ``datetime.datetime`` is, strictly speaking, a
  subclass of ``datetime.date``, we specifically detect and reject these inputs
  rather than accepting them and ignoring their time component. As before,
  rejection occurs by raising ``ValueError``.
* Some method parameter names have been updated to reflect the new date
  semantics. In particular:

   * :meth:`get_transactions <schwab.client.Client.get_transactions>`:
     ``start_date`` renamed to ``start_datetime``, ``end_date`` renamed to
     ``end_datetime``
   * :meth:`get_price_history_every_day <schwab.client.Client.get_price_history_every_day>`:
     ``start_datetime`` renamed to ``start_date``, ``end_datetime`` renamed to
     ``end_date``
   * :meth:`get_price_history_every_week <schwab.client.Client.get_price_history_every_week>`:
     ``start_datetime`` renamed to ``start_date``, ``end_datetime`` renamed to
     ``end_date``

* ``OptionSymbol``: ``expiration_date`` still accepts a ``datetime.date``
  or a ``YYMMDD`` string, but now rejects ``datetime.datetime`` rather than
  silently truncating it.
   
For completeness, here is a listing of the incorrect behavior of the previous
library. If you experience changes in behavior upon migrating, please check here
and check whether your code relied on buggy library behavior:

* Some endpoints (:meth:`get_orders_for_account <schwab.client.Client.get_orders_for_account>`,
  :meth:`get_orders_for_all_linked_accounts <schwab.client.Client.get_orders_for_all_linked_accounts>`,
  :meth:`get_transactions <schwab.client.Client.get_transactions>`) which
  accepted naive ``datetime``'s always
  formatted the value with a ``Z`` suffix. This meant a naive
  ``datetime`` would be passed to the API as though it was UTC, resulting in
  different behavior depending on the user's time zone.
* Those same endpoints *also* formatted timezone-aware ``datetime``'s with
  ``Z``, shifting the input value by a different number of hours depending on
  the user's time zone.
* Meanwhile, endpoints which passed values to the API as timestamps
  (:meth:`get_price_history <schwab.client.Client.get_price_history>` and the
  ``get_price_history_every_*`` helpers)
  converted naive ``datetime``'s using ``datetime.timestamp()``, which
  interprets the ``datetime`` as though it were in the user's local time, and
  then converts it to UTC. This represented an inconsistency in how naive
  ``datetime``'s were handled.
* Some methods (:meth:`get_orders_for_account <schwab.client.Client.get_orders_for_account>`,
  :meth:`get_orders_for_all_linked_accounts <schwab.client.Client.get_orders_for_all_linked_accounts>`,
  :meth:`get_transactions <schwab.client.Client.get_transactions>`) took dates
  while the underlying API endpoints took ISO datetime strings. These dates
  were converted to midnight UTC on that date,
  which for users west of UTC was not on the same calendar date as the input
  they had passed.

AI Disclosure
-------------

In keeping with the general tendency in our industry, development of
``schwab-py`` is now performed substantially using AI tools. These tools have
proven incredibly useful, and I've already been able to implement tasks in days
which I previously expected me to take weeks. I expect these tools will allow me
to create a more correct, feature-rich, and useful library than I would have
been able to deliver otherwise.

On the topic of correctness: AI thrives with concrete and specific feedback, and
to that end I am implementing a substantial functionality testing regime based
on placing real API calls against my personal Charles Schwab accounts. You may
inspect these tests in the
`livetests <https://github.com/alexgolec/schwab-py/tree/main/livetests>`__
directory of the codebase. If you spot anything suspicious, incorrect, or
incomplete, please let me know in the Discord server.
